## Тема: Віртуалізація та контейнеризація

---

## 1. Коротко, що треба знати перед захистом

### Віртуалізація
Віртуалізація дозволяє запускати кілька ізольованих середовищ на одному фізичному
комп’ютері. Класичний варіант — віртуальні машини (VM): у кожної своя ОС,
гіпервізор (VirtualBox, Hyper-V, VMware).

Плюси VM: сильна ізоляція.  
Мінуси: важкі, довго стартують, споживають багато RAM/CPU.

### Контейнеризація
Контейнер — це полегшена ізоляція процесу. Контейнери ділять ядро хост-ОС, але
мають власну файлову систему, процеси, мережу і залежності.

Docker — найпопулярніша платформа контейнеризації.

Порівняння коротко:
- **VM** = гість з повною ОС
- **Container** = ізольований додаток + лише потрібні бібліотеки

Саме тому контейнери швидші і зручніші для DevOps: однакове середовище на
ноутбуці студента, на CI і на сервері.

### Ключові поняття Docker
- **Image (образ)** — незмінний шаблон (snapshot) додатка з залежностями.
- **Container (контейнер)** — запущений екземпляр образу.
- **Dockerfile** — рецепт збірки образу.
- **Docker Compose** — спосіб описати і підняти кілька контейнерів разом
  (додаток + БД + інші сервіси).
- **Volume** — постійне сховище даних (щоб PostgreSQL не губив дані після
  перезапуску).
- **Network** — внутрішня мережа між контейнерами (`backend` ходить до `db`
  за іменем сервісу).

## 2. Який проєкт вибрано і чому

Обрано **DevOps Task Manager**:
- веб-додаток з UI;
- REST API;
- PostgreSQL;
- окремий мікросервіс сповіщень;
- unit/integration тести.

Це закриває всі пункти завдання і зручно розширювати в наступних лабораторних.

### Склад системи
1. **frontend** — інтерфейс користувача (Nginx роздає статику).
2. **backend** — бізнес-логіка завдань, робота з БД.
3. **notification-service** — приймає події «створено/оновлено/видалено».
4. **db** — PostgreSQL.

Чому це добре для DevOps:
- кілька Dockerfile;
- міжсервісна комунікація;
- є інфраструктурний компонент (БД);
- є тести для майбутнього CI.

## 3. Як побудовані Dockerfile

### Backend / Notification
Типовий Python Dockerfile:
1. бере базовий образ `python:3.12-slim`
2. копіює `requirements.txt`
3. встановлює залежності
4. копіює код
5. запускає `uvicorn`

Чому спочатку `requirements.txt`, а потім код?
Щоб Docker кешував шар із залежностями: якщо код змінився, а залежності ні —
збірка швидша.

### Frontend
1. бере `nginx:alpine`
2. копіює HTML/CSS/JS
3. роздає статику на порту 80

## 4. Що робить docker-compose.yml

Файл описує весь стенд:
- збирає образи сервісів;
- піднімає PostgreSQL;
- налаштовує змінні середовища (`DATABASE_URL`, `NOTIFICATION_URL`);
- відкриває порти на хост;
- чекає healthcheck БД перед стартом backend;
- зберігає дані БД у volume `postgres_data`.

Важливий момент для демонстрації:
всередині Docker-мережі сервіси звертаються одне до одного за іменами:
- `db:5432`
- `notification:8001`
- `backend:8000`

З браузера на хості ми ходимо на `localhost`, бо порти проброшені назовні.

## 5. Сценарій демонстрації перед викладачем (7–10 хв)

### Крок 0. Показати структуру проєкту
Показати папки:
- `backend/`
- `notification-service/`
- `frontend/`
- `docker-compose.yml`

Сказати: «Проєкт багатокомпонентний: UI, API, notification, PostgreSQL».

### Крок 1. Показати Dockerfile
Відкрити наприклад `backend/Dockerfile` і коротко пояснити шари образу.

### Крок 2. Підняти стек
```bash
docker compose up --build
```
Пояснити: Compose збирає образи і створює контейнери з залежностями.

### Крок 3. Показати, що все працює
```bash
docker compose ps
```
Усі сервіси мають бути `running` / healthy.

Відкрити в браузері:
- http://localhost:8080 — UI
- http://localhost:8000/docs — Swagger backend
- http://localhost:8001/docs — Swagger notification

### Крок 4. Жива перевірка бізнес-сценарію
1. У UI створити завдання «Підготувати захист лаби».
2. Показати, що воно з’явилось у списку.
3. Натиснути «Оновити» у блоці сповіщень — має з’явитись подія від backend.
4. Завершити/видалити завдання і знову показати нові notification-події.

Альтернатива через API:
```bash
curl http://localhost:8000/health
curl http://localhost:8001/health
```

### Крок 5. Показати ізоляцію і образи
```bash
docker images
docker ps
docker compose logs backend --tail=20
```
Сказати: кожен сервіс у своєму контейнері, з власними залежностями, але в
спільній мережі Compose.

### Крок 6. Показати персистентність БД
1. Створити завдання.
2. Перезапустити:
```bash
docker compose restart backend
```
3. Оновити UI — завдання лишилось, бо PostgreSQL дані у volume.

### Крок 7. Показати тести
```bash
docker compose run --rm backend pytest -q
```
Сказати: тести вже є і знадобляться в наступній лабораторній (CI).

### Крок 8. Зупинити
```bash
docker compose down
```

## 6. Готові відповіді на типові питання викладача

**Чим контейнер відрізняється від віртуальної машини?**  
Контейнер використовує ядро хоста і ізолює процес; VM піднімає окрему гостьову ОС.

**Навіщо Dockerfile, якщо можна просто встановити Python локально?**  
Dockerfile фіксує середовище: версії, залежності, команду запуску. Це усуває
проблему «у мене працює, а в тебе ні».

**Навіщо docker-compose, якщо є docker run?**  
Бо сервісів кілька. Compose описує їх разом: мережу, залежності, змінні, volumes,
порти — однією командою.

**Що таке volume?**  
Механізм збереження даних поза життєвим циклом контейнера.

**Чому backend залежить від db healthcheck?**  
Щоб API не стартував раніше, ніж PostgreSQL готовий приймати з’єднання.

**Чому окремий notification-service?**  
Щоб показати декомпозицію: окремий сервіс з окремим Dockerfile. Це фундамент для
мікросервісної архітектури в наступних лабораторних.

**Як сервіси знаходять один одного?**  
Через DNS імена сервісів у мережі Compose (`db`, `backend`, `notification`).

## 7. Мінімальний «шпаргалковий» текст (можна говорити майже дослівно)

«Для лабораторної я вибрав веб-проєкт Task Manager з кількох частин: frontend на
Nginx, backend на FastAPI, окремий notification-сервіс і PostgreSQL. Це закриває
вимоги: є веб-додаток, є база, є тести, є кілька компонентів.

Для кожного сервісу написаний Dockerfile, який збирає відповідний образ. У
docker-compose.yml описано весь стенд: збірка, мережа, змінні середовища,
healthcheck і volume для бази.

Однією командою `docker compose up --build` піднімається вся система. Користувач
працює через UI, backend зберігає завдання в PostgreSQL і надсилає події в
notification-сервіс. Таким чином я демонструю практичну контейнеризацію
багатокомпонентного застосунку.»

## 8. Критерії самоперевірки перед захистом

- [ ] `docker compose up --build` стартує без помилок
- [ ] UI відкривається на :8080
- [ ] Swagger backend відкривається на :8000/docs
- [ ] Створення завдання працює
- [ ] Сповіщення з’являються на :8001
- [ ] Тести backend проходять
- [ ] Можу пояснити різницю VM vs Container
- [ ] Можу пояснити Dockerfile і docker-compose своїми словами
